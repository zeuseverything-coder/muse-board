検証環境: Linux VM（共有CPU 1.5コア相当、メモリ約6GB）、Python 3.12。
ユーザーの実機（Windows）でしか確認できない項目は「未検証」と明示しています。

## 未検証（実機・追加環境が必要）

| 項目 | 理由 |
|---|---|
| WASAPIループバックでZoom/Meet/Teamsの相手音声取得 | Windows実機が必要（コードはPyAudioWPatchで実装済み） |
| イヤホン使用時にPC内部音声が取れるか | 同上 |
| 実マイクでの認識精度・遅延 | VMにマイク実機がないため。ブラウザマイク経路は実装済み |
| llama.cpp（GGUF）による代替LLM生成 | 追加の代替経路として導入を試行したが、llama-cpp-pythonの導入とGGUFモデル（約1GB）のダウンロードがこのVMの回線速度（未認証HFで約130KB/s）では完了せず断念。Ollamaが本命経路のため影響なし |
| Ollamaによる実LLM生成の品質・速度 | このVMではOllamaバイナリの配布経路（ollama.com / GitHub Releases）がプロキシ経由で取得できず導入不可。接続コードは実装済みで、未接続時はモックへ自動切替（状態APIで確認済み）。実機では `docs/MODELS.md` の手順で導入 |
| sentence-transformersバックエンド | torch等の容量・メモリ制約でVM未導入。インターフェース実装済み、未導入時はTF-IDFへ自動フォールバック（実測済み） |
| Silero VAD | 同上（任意機能）。エネルギーVADで代替し実測済み |
| PC・スマホ実機間の同期（同一LAN） | スマホ実機が必要。同一サーバーへの2クライアント同期は自動テストで検証済み |
| 切断→自動再接続→履歴復元（実機） | クライアント実装済み（再接続＋サーバー側イベント再生）。実機確認は未実施 |
| 60分連続使用の安定性 | 実機での長時間試験が必要 |
| 応答速度目標（AI生成の表示開始3秒・完成10秒） | LLM実機性能に依存。登録回答の即時表示（0.5秒目標）と同期（0.5秒目標）はVMで達成を確認 |
| 追加料金が発生しないか | ○ 設計上、有料API・外部送信なし（コードレビューで確認）。無料APIは未実装（任意選択肢として文書化のみ） |

## 測定値まとめ（VM参考値）

- 想定問答検索: 500ms未満（自動テスト上限として確認、実測は数ms〜数十ms級）
- WebSocket同期: 2端末間 212ms（answer_start到達）
- Whisper base: 実音声25秒を6.9秒で処理（このVM）。実機CPUではさらに高速化が見込める
- 部分文字起こし: 2秒ごとに再推論する設計。低スペック環境向けに部分推論ウィンドウを10秒に制限済み

## 未解決の問題と制約

1. **Ollama未導入環境ではモック生成になる**: 文章の自然さはLLMに劣る。実機でOllama＋モデルを導入すれば自動的にLLM生成へ切り替わる。
2. **Whisper baseの精度**: 漢字変換ミス等がある。実機では `small` / `medium` / GPU利用で改善可能（`docs/MODELS.md` に選定指針）。
3. **部分文字起こしの再推論コスト**: 長い発話では再推論が増える。ウィンドウ制限（10秒）で緩和済みだが、さらなる改善案は下記。
4. **質問判定はヒューリスティクス**: 挨拶・相づち・企業説明の除外はパターン依存。言い回しによっては誤判定があり得るため、手動トリガー（強制生成／修正して再生成）を常備。
5. **ブラウザマイクのサンプルレート変換は簡易実装**（間引き）。実機マイク利用時はホスト側マイクソース（sounddevice）の利用を推奨。

## 今後の改善案

- 発話途中からの先行検索（部分文字起こしの段階で想定問答を先読みし、確定直後に即表示）
- Whisperのストリーミング推論の最適化（LocalAgreement方式の確定テキスト管理）
- sentence-transformers導入時の埋め込みキャッシュ永続化
- 模擬面接モード（フェーズ3）: AIが面接官役で質問を出す練習モード
- 面接終了後の分析（フェーズ3）: 質問カテゴリ別の集計と弱点表示
- 回答の矛盾チェック強化: 過去回答との意味的一致を埋め込みで検証
